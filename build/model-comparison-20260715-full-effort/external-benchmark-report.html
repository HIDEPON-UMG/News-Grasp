00 — Verdict / Decision Support

意思決定者向けサマリ

どのモデルを、どの用途で、どの条件なら使うかを先に示す。単一の総合点で採否を決めない。品質トップでも運用主力とは限らないため、品質・費用・継続安定性・測定不能軸を分けて読む。

Model採用判断判断理由主要リスク次アクション
M1 GPT-5.5品質確認・根因分析・最終レビューの第一候補総合品質と要約系で最上位。複雑な判断の誤読リスクを下げる。高credit tierで、長時間実装主力にすると費用と制限到達が重い。ClosureStabilityとCostPerClosureを追加live runで確認し、主力化は1.5倍以内条件で判断する。
M2 GPT-5.6 Terra同credit tierの主力候補だが、現時点ではGPT-5.4同等疑いを維持日本語NLUで強みはあるが、総合・repair・summaryでGPT-5.4を安定して引き離していない。Terra が GPT-5.4 程度か、という仮説を棄却するには長時間復旧のVCR/OSR証拠が足りない。30-90分のCodex recovery telemetryを3回以上追加し、fallback・resume・public verifier到達率を見る。
M3 GPT-5.6 Luna低credit/高速候補として独立評価し、Terra/GPT-5.4の代替線に置く公式 rate card 上は Luna がさらに低credit tierで、短時間・低負荷タスクの主力候補になりうる。低effortや低costが品質劣化を隠す可能性があるため、coding/summary/recoveryをeffort別に分けて読む必要がある。low/medium/high の3 repetition平均を揃え、品質低下とCostPerClosureの交換条件を判定する。
M4 GPT-5.4低credit baselineとして維持し、Terra比較の基準にするCODE_SYNTHで安定し、費用帯もTerraと同じ。Terra優位判定の最低比較線になる。要約・複合復旧では上位モデルに劣る可能性があり、主力化にはclosure証拠が不足。同一fixture・同一順序ローテーションで平均と分散を継続比較する。

追加で必要な証拠: Terra が GPT-5.4 程度かを確定するには、同一fixtureの最低3回平均に加えて、30-90分 recovery task のVCR/OSR、fallback、resume、public verifier到達率が必要。

05 — Evaluation Design

Score Method

正本は AI-Pulse の過去ローカルLLM調査。1-5の factual / summary / points / rationale / overall 軸、N=11、採点済み 10、completion rate と latency の分離を要求する。今回は盲検実施済みとは主張しない。

HumanEval / MBPP 型は実行テスト、SWE-bench / LiveCodeBench 型はpatch + pytest、JGLUE型は根拠span、XL-Sum型は事実反転・禁則主張検出で扱う。

品質、安定性、形式制御、速度、VRAM、日本語品質、重みは同じ総合点に混ぜない。品質はcase oracle、安定性は反復stdev、形式制御はformat violation、速度/VRAM/creditsは運用ゲート、日本語品質はJA_NLU/JA_SUMMARY、重みはDecision Matrix側で分離する。

– — Measurement Limit

Measurement Limit

このレポートは external benchmark design grounding を使ったlocal matrixであり、HumanEval / MBPP / SWE-bench / JGLUE / XL-Sum 本体スコアではない。tool-callingや90分連続自走の実能力はproxyで捏造せず、別telemetryが必要。

– — External Benchmark Grounding

External Benchmark Grounding

  • HumanEval: code synthesis is judged by executable unit tests, not explanation quality
  • MBPP: small Python programming tasks include task text, reference code, and automated tests
  • SWE-bench: repo repair ability is measured by applying a patch and running tests
  • LiveCodeBench: coding evaluation should avoid one undifferentiated easy case and should separate generation and repair
  • JGLUE: Japanese natural language understanding should be evaluated as Japanese tasks, not translation-only proxies
  • llm-jp-eval: Japanese LLM evaluation should use multiple dataset-style task families and mechanical scoring where possible
  • XL-Sum: summarization should be grounded in source text and checked for concise factual preservation
  • Open Japanese LLM Leaderboard: Japanese leaderboard practice separates tasks such as NLI, QA, summarization, and code
