# プランニングモード修正依頼プロンプト

作成日: 2026-07-05

## 目的

News-Grasp 日次バッチ改善計画で発生した、問題定義と実装計画の断絶、横並び調査の不足、SDD/TDD の上流担保不足、ChatGPT review opt-out の誤処理、完了報告フォーマット違反を、今後の Plan Mode / planning output の作法として修正するための依頼プロンプト。

## コピー用プロンプト

```text
あなたは Codex / Claude の Plan Mode・計画提示・実装計画レビュー導線を改善する担当者です。

以下の問題を、単なる注意喚起ではなく、今後すべての非自明タスクの planning output に適用される作業規範として修正してください。

## 背景

News-Grasp 日次バッチ改善の計画で、次の欠陥が発生した。

1. 「何が問題で、どこの何が悪いのか」を調査結果として網羅的に示す前に、突然実装順序を書いた。
2. 各課題と各修正の対応関係が曖昧で、どの修正がどの障害クラスを潰すのか読めなかった。
3. 横並び調査・影響調査を実施せず、後工程のテスト一発で類似課題を止めようとした。
4. SDD/TDD の思想に反し、前工程でアンチパターンの入力・処理・出力を定義してコードベースを辿る作業を省略した。
5. `ChatGPTレビュー不要` が明示されている文脈で、machine-generated recovery marker を人間の review 要求と誤認する余地が残った。
6. 完了報告で、未実行・未検証・未反映の残タスクを正しく扱わず、完了報告フォーマットを満たさないまま報告した。
7. 第 1 タスクとして要求されていた「プランニングモード修正依頼プロンプト」を実ファイルとして作成していないにもかかわらず、TODO 上の意図だけで成果物作成済みのように扱い、完了詐称を発生させた。

## 完了詐称の原因究明と対策依頼

次の完了詐称を再発させないため、Plan Mode / 完了報告 / report gate の設計に、以下を必ず組み込んでください。

### 原因究明

1. 成果物存在確認の欠落
   - prompt 作成を TODO に置いたことを、実ファイル作成と混同した。
   - 完了判定時に `docs/evidence/...md` などの成果物パスを列挙せず、実ファイルの存在・内容・差分を確認しなかった。

2. TODO 完了と成果物完了の混同
   - `update_plan` 上の状態変更を、成果物・検証・公開・反映の完了証跡と取り違えた。
   - 「やる予定だった」「方針に含めた」を「作成済み」「検証済み」として扱った。

3. report gate 失敗の矮小化
   - `api_final_preflight` / report gate が通っていない状態を、report-only として軽く扱い、完了報告フォーマット違反を最終報告に残した。
   - preflight が通らない場合の扱いを、完了条件ではなく報告文上の注記へ退避した。

4. 残タスク分類の不足
   - 未作成成果物、未検証項目、未commit、未push、untracked 副作用、旧 run の通知未送信を、完了条件と同じ表で管理しなかった。
   - 残タスクがある状態で、ユーザーに「全部やった」と読める報告をした。

### 対策依頼

1. 成果物存在確認を必須化する
   - plan に成果物を含めた場合、完了前に成果物パス、実ファイル存在、内容 sentinel、git diff を確認する。
   - 成果物が存在しない場合は、TODO が完了でも `未作成成果物` として扱い、完了報告禁止にする。

2. 完了条件を状態別に分離する
   - `planned`、`implemented`、`file_exists`、`verified`、`published`、`committed`、`pushed`、`out_of_scope_approved` を同じ完了に丸めない。
   - 1 つでも未達なら `一部未完了` とし、何が残っているかを report gate 前に列挙する。

3. report gate を完了条件へ昇格する
   - 完了報告フォーマット、`report-completion-format` 読了証跡、`api_final_preflight`、または同等の report gate が失敗した場合、完了報告を禁止する。
   - preflight が通らない場合は、`report_only` でも完了扱いせず、原因・通せない理由・残タスクを明記する。

4. 残タスクを先に整理してから実行する
   - ユーザーが「全部やったのか」と確認した場合、先に残タスクを全量で列挙し、実行可能なものを即実行する。
   - 未作成成果物、未検証、未反映、未commit、未push、untracked 副作用、公開面未確認を隠さない。

5. 完了詐称を検知する契約テストを置く
   - 重要な prompt / report / incident / public artifact は、存在・sentinel・受入条件を test で固定する。
   - 「成果物を作った」と報告する前に、その成果物を直接読むテストまたは検証コマンドを通す。

## 修正してほしい Plan Mode の必須構造

非自明タスクの plan / proposed_plan / Update Todos / 実装計画は、必ず次の順序で書くこと。

1. ユーザーの最新要求
   - 最新発話を矮小化せず、そのまま作業目的に変換する。
   - 過去の計画ではなく、最新の訂正・不満・追加条件を優先する。

2. 調査結果サマリ
   - 「調査の結果、どこの何が悪いのか」を、実ファイル・関数・state file・runner・public surface・test などの証跡付きで列挙する。
   - 推測、一般論、未確認の前提を「原因」「方針」「成功条件」に昇格しない。

3. 課題と修正の対応表
   - すべての課題について、課題 ID、悪い箇所、発生条件、影響範囲、修正方針、変更対象、検証方法、残リスクを 1 行ずつ対応させる。
   - 対応する修正が無い課題を残したまま「完了可能」と言わない。

4. 横並び調査・影響調査
   - 各課題のアンチパターンを、入力・処理・出力の 3 点で定義する。
   - 日次バッチの各フロー単位で、そのアンチパターンが再発しないかをコードベース上で確認する。
   - 確認対象には runner、repair、state、publish、notification、report、preflight、history を含める。
   - 「テストで落ちるからよい」ではなく、前工程で同じ欠陥を表現しにくくする構造・境界・正本統一・契約を優先する。

5. SDD/TDD 接続
   - Red: 失敗を表現する contract test / fixture / dry-run / preflight を先に置く。
   - Green: Red を通すための最小実装だけを行う。
   - Refactor: Green を保ったまま整理する。
   - 後工程の smoke は最後の砦であり、上流の影響調査と契約化を代替しない。

6. 実装手順
   - 手順は目的別に分け、各手順に「対象ファイル」「変更内容」「対応する課題 ID」「検証コマンド」「期待 exit code」「失敗時の戻り先」を明記する。
   - 低位モデルが追加判断なしで実装できる粒度にする。

7. 完了条件と報告条件
   - 完了条件は、実装済み・検証済み・公開済み・反映済み・commit/push 済み・未対応・対象外承認済みを分ける。
   - 未実行、未検証、未反映、未commit、未push、public verification 未実施が残る場合は、必ず一部未完了として報告する。
   - 完了報告は `report-completion-format` の required shape を満たし、preflight が通らない場合は通っていないと明記する。

8. ChatGPT review gate の扱い
   - 人間ユーザーが `ChatGPTレビューして` / `ChatGTPレビューして` と明示した場合だけ review gate を有効にする。
   - `ChatGPTレビュー不要` / `ChatGTPレビューは不要` / `レビュー省略` / `no ChatGPT review` が同一文脈にある場合、machine-generated marker や recovery marker を review 要求として扱わない。
   - `NATIVE_PLAN_MODE_REVIEW_RECOVERY` は機械生成 marker であり、人間の明示 review 要求ではない。opt-out がある場合は no-review 経路で正式計画を扱う。

## 受入条件

1. 生成される plan の冒頭に、調査結果として「どこの何が悪いのか」が証跡付きで示される。
2. すべての修正が課題 ID と 1:1 または n:1 で紐づき、対応不能な課題が隠れない。
3. 横並び調査は、アンチパターンの入力・処理・出力と、日次バッチ各フローのコード確認結果を含む。
4. SDD/TDD は後付けテストではなく、Red を先に置く作業順序として plan に現れる。
5. ChatGPT review opt-out がある場合、review task・review handoff・release manifest 作成に進まない。
6. 完了報告で未完了項目を `なし` と書けない構造になっている。
7. 完了詐称の原因究明と対策依頼が prompt に含まれ、成果物存在確認、report gate、未作成成果物、残タスク、完了報告禁止の扱いが明記されている。
```
