02

問題の詳細と、なぜ起きたか

直接原因
停止した E2E をその地点から継続せず、fresh rerun と遅延予約へ寄せたため、下流 bug の洗い出しと06:00締切の逆算が遅れた。本来は 停止点を保存 し、pre-DeepDive終端まで継続探索 してから一括修正すべきだった。
検証対象
News-Grasp の daily publish state machine のうち、DeepDive記事作成前まで。
なぜ必要か
過去障害と今回障害は、すべて DeepDive記事作成前の工程 で発生している。単発の正常系E2Eでは、repair / fallback / typed external / inventory の相互作用を捕まえられない。
検出すべき異常
deterministic repair後の残留Red、NoPublish時のfallback public副作用、typed external block と local Green のpublish完了合成、曜日inventoryとdistribution manifestの境界崩れ。
完了表現の境界
local / NoPublish の完走は public 完了ではない。公開面、live runner、翌日Scheduled Taskは別証跡で確認するまでYellowで残す。
2次
二次的に見つかった問題

前回報告は図の存在だけを契約にしていたため、読める工程図かどうか、また障害レポートのトンマナに合っているかを検出できなかった。

05

恒久対応方針の網羅性と完璧性の担保

完璧性の定義

ここでいう完璧性は「未知の全障害が絶対に起きない」ではなく、今回と同じ class の失敗が再導入された場合に、E2E後レポートと契約テストで どの工程で検出・修復・停止されたかを読めること と定義する。

Layer 1
本番量を正本resolverで固定

曜日カテゴリを手書きせず、repoのsource of truthから解決する。

Layer 2
repair後の残留赤を止める

deterministic repair後も同じgateを再実行し、残留RedをGreen扱いしない。

Layer 3
NoPublish副作用を禁止

fallback publish、push、upload、notificationへ進まないことを固定。

Layer 4
typed external blockを分離

外部障害blockはシナリオPASSだが、local Greenと混ぜてpublish完了扱いしない。

Layer 5
PowerShell衝突をfixture化

CapturePath / StatePath のscriptblock scope衝突を落とす。

Layer 6
E2E後HTMLを必須化

E2E実行は、障害レポート準拠HTMLが残るまで報告完了にしない。
