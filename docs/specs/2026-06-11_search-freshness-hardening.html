ニュース検索鮮度の構造対策

古い記事が候補選別を素通りするクラスのバグを、選別境界 dedup 1 箇所の強化で構造的に封じる（06-10 号 29 件中 14 件古記事の根本対策）。

draft News-Grasp タスク③

概要

2026-06-10 号は 29 件中 14 件が独立証拠（htmldate / Wayback CDX）と 6〜854 日乖離した古記事だった。push 前 gate（tools/audit_all_article_urls.py --gate --verify-dates、2026-06-11 実装済み）は最終防衛として機能するが、検索・選別段階の歩留まりが悪いままだと号の半分が gate で死に、再発行が成立しない。

調査の結果、原因は 3 層に分かれる。

層実測事実素通り条件
WebSearch ツールパラメータは query / allowed_domains / blocked_domains のみ。日付・鮮度パラメータは存在しない（スキーマ実測）検索段階では構造的に鮮度を保証できない
選別境界 tools/dedup.pyURL パス日付の認識は /YYYY/MM/DD/ 等 4 形式のみ。/YYYY/MM/（月まで）の URL は None で素通り。crowdfundinsider /2026/01/・thediplomat /2026/04/ がこの穴URL に日付が無い／月までの候補は freshness gate を素通り
LLM 選別規律06-10 it.json で LLM が自由裁量の「editorial: background context」により 2026-01 の古記事を意図的に採用（プロンプトに規定なし = LLM の発明）LLM 裁量が gate 思想と矛盾。新 push gate 下では fatal になり号が落ちる
前提

tools/append_after_dedup.py は freshness gate がデフォルト ON で、articles.jsonl への唯一の取込経路（決定論的境界として既に機能）。dedup.py の強化 = 実境界の強化になる。1 class of bugs = 1 チェックの原則に従い、push 前 gate（「公開物に載る」の最終防衛）と検査を重複させない。

ユーザー決定（2026-06-11）

URL でも htmldate でも公開日が取れない候補は warn-pass（誤爆ゼロ運用を維持、push 前 gate が最終防衛、運用観察後に厳格化判断）。htmldate 補完と runner 当日日付注入は採用、search_audit クエリ日付語 lint は不採用。

採用 / 不採用の判断

dedup 境界の強化

採用

月単位 URL パターン追加 + htmldate 補完 + published_date 注釈。articles.jsonl への唯一の取込経路である決定論コードに集約するため、LLM がバイパスできない。トレードオフ: htmldate 補完は候補 1 件 1 GET で dedup 実行が数十秒〜数分延びる。

search_audit への鮮度メタ自己申告

却下

LLM の自己申告日付は偽日付事故の根本原因そのもので信頼できない。push 前 gate と検証が重複し、1 class 1 チェック原則にも反する。

LLM 手順への date_evidence 必須化

却下

routine-system.md の手順指示は LLM セッション内でバイパス可能。dedup 内蔵（決定論コード）で代替する。プロンプトには補助の規律（editorial 禁止・日付語指針）のみ追記。

クエリ日付語 lint

却下（ユーザー確認済み）

クエリは LLM 自己申告で偽装可能なうえ、日付語強制が recall を下げるリスクが未検証。効果が弱い割に誤爆リスクがある。

WebSearch 鮮度演算子（after: 等）への依存も却下

ツールスキーマに鮮度パラメータは存在せず、クエリ文字列演算子の実効性は未検証。検証コストが効果見込みを上回るため、クエリへの日付語付加（規律・補助）に留める。

データフロー

強化後の鮮度判定は dedup 内で 3 段（URL 日単位 → URL 月単位 → htmldate 補完）。どこでも解決できなければ warn-pass し、push 前 gate が最終防衛する。

実装ステップ

1.dedup.py: 月単位パターン + htmldate 補完 + published_date 注釈
2.routine-system.md: editorial 禁止・日付確認手順・クエリ日付語指針
3.runner.ps1: 当日日付のプロンプト注入
4.契約テスト → pytest 全体 → E2E 実測

コード断片（月単位パターンと判定方針）

# tools/dedup.py — _URL_DATE_PATTERNS に追加する月単位パターン（月粒度フラグ付きで返す）
_URL_MONTH_ONLY_RE = re.compile(
    r"/(?P<y>20\d{2})/(?P<m>\d{1,2})(?:/(?!\d)|/$|$)"  # /2026/01/ の直後が「日」でない
)
# 判定方針:
#   日単位日付 → 既存どおり max-source-age-days で判定
#   月単位日付 → 候補の月 < 許容下限(min_allowed_date)の月 なら DROP
#               同月は粒度不足として通す（push 前 gate が日単位で捕捉）
#   どちらも無し → date_evidence.fetch_html + extract_published_date で補完
#               古い → DROP / 取れない・fetch 失敗 → warn-pass（stderr に警告）
#   解決できた公開日は record["published_date"] / record["date_evidence_source"] に注釈

検証

  • pytest tests/ 全体 PASS（NEWS_GRASP_SKIP_URL_CHECK=1、契約テスト追加後に既存 336 件 + 新規が全件 PASS であること）
  • E2E: 今朝の検体 data/_tmp_*_candidates.jsonl を強化後 dedup に通し、月単位 URL の古記事が DROP・当月記事が pass（誤爆ゼロ）を実測
  • runner 日付注入はプロンプト組み立ての dry-run で注入文字列を実測確認

既定値の根拠

max-source-age-days=1 は現行運用（当日+前日のみ許容）の踏襲。timeout=15 秒は date_evidence.fetch_html の既定値と同一。上限件数 20 は 1 カテゴリの候補が通常 10〜30 件であることから、dedup の実行時間悪化（1 件 1 GET）を抑える安全弁。
