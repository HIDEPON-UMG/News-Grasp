OVERVIEW

目的と成功条件

今回の根本原因候補は timeout そのものではない。通常 30 分程度で終わる処理が 1 時間に達し、記事の半分も作られなかったことから、収集、要約、gate 修復のどこかで同じ失敗を繰り返せる構造が疑われる。

成功条件は三つに分ける。Content Gate を通った本日号だけを通常公開する。本日号が通らない場合は fallback notice 付きで直近成功号を維持する。secret、security、破壊的変更の疑いだけは自動公開せず停止する。

Claude の責務 digest 生成に加え commit まで prompt で要求され、gate を意識した自己修復が膨らみ得る。 Claude は生成 worker と bounded repair worker に限定する。commit、push、docs 生成、publish gate は runner が管理する。
gate 失敗 失敗メッセージは人間向けで、同じ失敗署名を何度繰り返したかが runner に残らない。 failure_signature と artifact hash を記録し、同一失敗は 1 回だけ修復、カテゴリ最大 2 回で fail-fast する。
公開保証 Content Gate 失敗時は push 前に止まり、朝に公開面が更新されない可能性が残る。 Content Gate 失敗時は通常号を出さず、直近成功号に品質確認中 notice を入れて Availability Gate を通して公開する。

IMPLEMENTATION

実装ステップ

Phase 0

本仕様書を作成し、HTML 仕様書が実装前の判断材料になる状態を固定する。

Phase 1

既存 runner、wrapper、prompt、hook、gate 出力を棚卸しし、同じ失敗を繰り返せる場所を runner 境界へ移す。

Phase 2

gate failure contract と attempt state を実装し、失敗署名、対象 artifact、修復可否を記録する。

Phase 3

runner に bounded retry と fallback publish を追加し、Content Gate と Availability Gate を分離する。

Phase 4

Claude prompt を生成専用へ縮小し、commit/push/docs 生成を runner 側に戻す。

Phase 5

session URL 欠落は silent skip にせず、強警告と audit log の存在確認を runner ログへ出す。
