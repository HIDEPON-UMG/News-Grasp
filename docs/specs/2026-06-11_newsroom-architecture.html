News-Grasp Newsroom Architecture

日次 digest 生成を「編集長 (Sonnet メイン) + カテゴリ記者 (Sonnet サブエージェント並列 ×7) + エース記者 (Opus サブエージェント)」体制へ移行し、所要 70 分超 → 30-35 分と品質構造（横断 dedup・date=号日 gate・白リスト hook race 封じ）を同時に実現する。あわせて収集改善（RSS ハーベスタ + クエリ規約改訂 + Scrapling fetch 昇格ラダー）を統合する。

draft News-Grasp ユーザー確認待ち（実装は確認後） 収集改善 A+B+Scrapling

概要

現行の日次 digest 生成は、1 つの claude -p セッションが 7 カテゴリ（fx / ai / it / mobility / manufacturing / economy / game）を直列処理しており、鮮度ゲート工程の追加で所要時間が 70 分を超え TimeoutSec 3600 に接近している。本仕様は処理をニュース編集部のメタファーで再構成する。

体制図

前提・制約（公式根拠取得済み）
  • headless (claude -p) で Agent ツール利用可。PermissionRequest は発火しないが、wrapper は --dangerously-skip-permissions --tools default 起動のため permission 設計は現状のままで足りる。
  • hooks はサブエージェント内のツール実行にも発火する（白リスト hook が記者の WebSearch を捕捉できる根拠）。
  • .claude/agents/*.md frontmatter でサブエージェント毎に model 指定可（記者 = sonnet / エース = opus）。
  • runner.ps1 の呼び出し形態（wrapper / cwd=リポ / PromptFile / 日付ヘッダ注入）は不変。cwd=News-Grasp 以外では session URL hook が発火しないことを実測済み。
  • 並列規模は公式想定の「数個」レンジに収める（既定 7 体同時、429 発生時は段階投入へ）。
06-11 号で実害が確定した構造課題（本仕様で封じる）
  • カテゴリ別分割 dedup がカテゴリ間重複を素通し（Decart が AI+Mobility、indexbox が FX+Economy の 2 組）。
  • articles.jsonl の date=号日 規約が機械検査されず 21 件誤記。
  • 白リスト hook (append_session_urls.py) は read→union→replace 構造のため、並列サブエージェント同時発火で後勝ち消失する（atomic replace でも union 元が古い）。
  • 上流収集が古記事を引く（search_audit 集計: raw 144 → 候補 65 → 採用 27。drop 42 件中 36 件 = 86% が freshness gate。WebSearch に日付・鮮度フィルタが構造的に存在せず、当月日付語クエリ（"CPI inflation report May 2026" 等）が古記事を能動的に引いた実害がある）。
本調査での新規発見リスク

並列サブエージェント待機中、メインセッションの stream-json stdout が長時間沈黙する可能性があり、IdleTimeoutSec 900（15 分無出力 kill）が偽発動し得る。V1 検証で wrapper の heartbeat ログ（60 秒毎 idle=Ns）から max idle を実測し、初週は 1800 へ引き上げてから実測値で確定する。

成功条件

  • 三段検証（V1 / V2 / V3）PASS 後、翌朝の Task Scheduler 本番で publish gate 全 PASS。
  • 公開サイト（GitHub Pages）の当日号が 200 で見える（ユーザー可視成果で完了判定）。
  • digest 生成の所要時間が 30-35 分（TimeoutSec 3600 に余裕）。
  • カテゴリ間重複 0 件・date=号日 違反 0 件・session 白リスト欠落 0 件が gate で機械保証される。
  • freshness gate での drop 率が大幅減少する（RSS ハーベスタ + when:1d クエリで収集段階で直近 24h に絞られており、dedup の freshness gate は最後の防衛線に降格している）。

採用しなかった案

論点 1: 白リスト hook の並列 race 対策

フラグメント方式

採用

hook は発火毎に data/_session_urls.d/{日付}/{uuid4}.json を新規作成のみ行う。共有可変状態が消えるため race が表現不能（Lv1: illegal state unrepresentable）。読み側 (audit_all_article_urls.py --match-session) がフラグメント群 + legacy ファイルを union。

ファイルロック

却下

msvcrt.locking 等で read-modify-write を排他。race を「縮める」だけの Lv2 止まりで、Windows 特有のロック待ち / orphan lock / AV 干渉という新しい失敗モードを hook（timeout 30 秒）に持ち込む。

編集長の最終照合

却下

編集長が記者の報告 URL を白リストへ再集約する案。白リスト生成が LLM の規律に戻り、hook 化（2026-06-05 案③ = ハーネス層が直接記録するから捏造を封じられる）の存在理由そのものを破壊する。

論点 2: カテゴリ間重複の封じ方

編集長の dedup 第 2 パス

採用

dedup.py は既にバッチ内重複を弾く（合格分を既存プールに積み増す実装）ため、全記者の records を連結して 1 回通すだけでカテゴリ間照合が成立する。判定は機械（dedup CLI）であり LLM 判断に依存しない。

記者間の相互参照

却下

各記者に他カテゴリの採用 URL を渡して自主回避させる案。並列実行中は他記者の選定が未確定のため原理的に不完全で、記者間の依存（待ち合わせ）が並列化の利得を壊す。頻発カテゴリ対だけの事前ヒントとしては将来検討余地（V2 で頻度観測）。

論点 3: DeepDive の移行方式（ユーザー判断確定済み）

一斉移行

採用

V3 切替と同時にエース記者サブエージェントを有効化し、runner.ps1 step 2.5（別プロセス Opus DeepDive）を削除する。移行が 1 回で済む。エース記者の spawn は Summary 執筆 + append 完了後なので、失敗しても digest 成果物は確定済み = 構造的に非致命。

段階移行

却下

初週は step 2.5 を温存し記者並列だけ先に安定させる案。切替変数が 1 つずつになり障害切り分けは容易だが、移行が 2 回になり、デュアル経路の維持コストが掛かる。ユーザー判断で一斉移行を選択（2026-06-11）。

論点 4: 基盤 4 点の投入タイミング（ユーザー判断確定済み）

先行デプロイ

採用

hook フラグメント化 / validate_record --issue-date / dedup 注釈 carry-over / verify_reporter_output.py は旧直列体制でも後方互換で動くため、新体制切替前に投入して翌朝の本番で慣らす。切替日の変更点を「プロンプト + 並列化」だけに絞れる。

一括切替

却下

基盤も新体制と同日に投入する案。デプロイ回数は 1 回で済むが、切替日に問題が出たとき基盤起因か並列化起因かの切り分けが難しくなる。

論点 5: 上流収集の改善方式（2026-06-12 確定）

A+B 併用（採用）

採用

RSS ハーベスタ（tools/harvest_candidates.py）が Google News RSS + when:1d で pubDate 付き候補 jsonl を事前生成（決定論 CLI・claude 起動前に runner.ps1 が実行）。取得前に pubDate で鮮度を機械判定できるため freshness gate は最後の防衛線に降格。WebSearch はイベント・エンティティ駆動クエリの補完に限定する。クエリ規約改訂（B）で過去月日付語を禁止し、当日・前日のみ許可。

鮮度ゲート強化のみ

却下

既存の freshness gate のしきい値を厳しくする案。ゲートは既に誤爆ゼロで正常動作している（86% drop は正しく古記事を弾いている）。真因の上流収集を放置したまま強化しても候補が痩せるだけで根本解決にならない。

WebSearch クエリ工夫のみ

却下

クエリへの日付語追加・言い換えで鮮度を改善する案。WebSearch ツールの schema には allowed_domains / blocked_domains しかなく、日付・鮮度フィルタが構造的に存在しない。"CPI inflation report May 2026" 型の当月日付語が古記事を能動的に引いた実害があり、クエリ側の工夫は構造的限界がある。

論点 6: Google News RSS の canonical URL 解決方式（2026-06-12 確定）

site: 限定 WebSearch

採用

RSS の <source url> 属性で媒体ドメイン・タイトルを取得し、site:reuters.com "記事タイトル" 形式の WebSearch で実 URL を確定する。session URL 白リスト hook が WebSearch URL を自動捕捉する既存フローと完全整合し、捏造防止フロー（audit --match-session）がそのまま機能する。

googlenewsdecoder

却下

PyPI に存在する googlenewsdecoder ライブラリで Google 内部 API を呼ぶ方式。Google の内部 API 変更で予告なく破壊されるリスクがある。依存度が高く、障害時に代替手段がない。

link 直接 GET

却下

RSS の <link> 要素を直接 GET する方式。<link> は JS 必須のエンコード URL（news.google.com/rss/articles/CBMi…）で、単純 GET では媒体ページへ解決されないことを実測確認済み。

論点 7: BOT 対策ドメインの fetch 方式（2026-06-12 実打確認・採用確定）

Scrapling 昇格ラダー境界集約

採用

tools/_fetch.py に fetch_with_escalation() を 1 箇所集約（境界モジュール）。urllib → Fetcher（curl_cffi 偽装・ブラウザ不要） → StealthyFetcher（ヘッドレスブラウザ）の昇格ラダー。403 / blocked 検知時のみ昇格し、StealthyFetcher は最終段限定。0.4.9 に pin（0.4.x で css_first 廃止 → css() に変更）。適用 4 箇所（fetch_ogp / date_evidence / audit_all_article_urls / ハーベスタ canonical 解決補助）はすべてこの関数を呼ぶ。

各ツール個別導入

却下

fetch_ogp / date_evidence / audit / ハーベスタの 4 箇所に Scrapling 呼び出しを個別実装する案。境界集約原則に違反し、Scrapling API 変更（css_first → css() のような）が 4 箇所の個別修正を要求する。

ヘッドレスブラウザ常用

却下

StealthyFetcher を全リクエストに常用する案。1 fetch 数秒〜十数秒かかるため、日次 run の全 OGP 取得・生存確認に適用すると所要時間を破壊する。urllib で 200 が返るリクエストに重量フェッチャーを使う必要はない。

コンプライアンス注記（Scrapling 利用範囲）

Scrapling の用途は OGP メタ取得・発行日メタ取得・URL 生存確認に限定する。paywall 本文の取得回避には使わない。robots_txt_obey フラグの利用を検討する。

データフロー

記者の成果物はすべてファイル経由で編集長に渡る。Task 返却（メイン文脈に載るもの）はコンパクト JSON（約 2KB）のみ。記事本文・フル record・digest md 本文はメイン文脈に一度も載らない（2026-05 の 415 万トークン破綻の構造的再発防止）。

収集の上流化（2026-06-12 追加）: runner.ps1 が claude 起動前に tools/harvest_candidates.py を決定論 CLI として実行し、Google News RSS + when:1d クエリで pubDate 付き候補 jsonl を生成する。06-11 実測: raw 144 → 候補 65 → 採用 27。drop 42 件中 36 件（86%）が freshness gate（古記事）だった。RSS の各 item に pubDate (RFC822) が付くため、取得前に鮮度を機械判定できる（freshness gate は最後の防衛線に降格）。

収集フロー（ハーベスタ → 記者 → dedup）

注: watchlist 主要媒体の公式 RSS も候補ソースとして併用（link 直接取得・canonical 解決不要）。

ハーベスタ出力 jsonl（1 行例）

主要コード断片（hook フラグメント化の核）

# append_session_urls.py — merge_into_session_file() を置き換え
def write_fragment(new_urls: set[str], today_str: str, fragments_root: Path) -> Path:
    """発火 1 回 = フラグメント 1 ファイル新規作成。共有可変状態なし = race 表現不能。"""
    day_dir = fragments_root / today_str          # data/_session_urls.d/2026-06-12/
    day_dir.mkdir(parents=True, exist_ok=True)
    frag = day_dir / f"{uuid.uuid4().hex}.json"   # 衝突しない一意名・上書きなし
    frag.write_text(
        json.dumps({"date": today_str, "urls": sorted(new_urls)}, ensure_ascii=False),
        encoding="utf-8",
    )
    return frag

# audit_all_article_urls.py — 読み側は union（破損フラグメントは 1 件単位 warn-skip）
def load_session_urls(repo: Path, today_str: str) -> set[str]:
    urls: set[str] = set()
    for frag in sorted((repo / "data" / "_session_urls.d" / today_str).glob("*.json")):
        try:
            urls |= set(json.loads(frag.read_text(encoding="utf-8")).get("urls", []))
        except (json.JSONDecodeError, OSError):
            print(f"WARN: broken fragment skipped: {frag}", file=sys.stderr)
    # legacy _session_urls.json も当日 date なら union（移行期互換）
    ...
    return urls

パラメータ

新体制の運用パラメータをスライダーで確定し、最後に「プロンプトとしてコピー」で Claude Code に戻してください。実装はこの値で進めます。

7 体

7 = 全カテゴリ同時（最速・429 リスク高め）。4 以下 = 段階投入（4+3 の 2 wave。wave 間に編集長イベントが入り IdleTimeout にも安全側）。

1800 秒

並列サブエージェント待機中の stream-json 沈黙による偽 kill 回避。V1 実測 max idle < 300 秒なら安定後 900 へ戻す。

1 回

超過後は PASS 分のみ採用 + quality_shortfall_reason 確定（既存 fallback 経路）。2 にすると品質は上がるが所要時間 +10-15 分のリスク。

5 件

現行運用は 5 件。変更すると validate_daily_quality の件数基準も連動改修が必要。

20 分

編集長がエース記者 spawn 時にプロンプトで指示する目安時間。超過しても digest は確定済みのため非致命（セッション全体は TimeoutSec 3600 が上限）。

50 件

Google News RSS は 1 feed 最大 100 件。多いほど選択肢が増えるが canonical 解決（site: 限定 WebSearch）の件数も増える。

10 件

1 fetch 数秒〜十数秒。0 = Fetcher までで打ち切り（bloomberg 等は thumb null 継続）。
