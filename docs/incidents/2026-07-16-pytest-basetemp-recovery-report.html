Fault boundary · 停止した工程

停止点はコンテンツ生成ではなく、公開前 gate の pytest-static。runner は PYTEST_ADDOPTS=--basetemp=.pytest-tmp を使うため、fixture root が repo 配下になる。監査 tool は git ls-files の repo 相対出力を fixture root 相対に誤変換し、retired model fixture を走査しなかった。これにより契約テストが失敗し、壊れた状態の push を防いだ。日次バッチは起動済みで、digest・Summary・DeepDive・audio-script までは生成済みだったため、generate_pages.py と git push に到達せず、公開面は前日 2026-07-15 のまま残った。

02

問題の詳細と、なぜ起きたか

直接原因
tools/audit_runtime_model_dependencies.py が指定された repo_root ではなく親 git worktree の相対パス前提で候補を解決していた。runner 同等の --basetemp=.pytest-tmp 条件では tmp fixture が repo 配下に置かれ、retired model fixture を見落として status=pass を返した。
なぜ起きたか
通常の単体実行では tmp_path が repo 外に作られるため fallback 走査で成功した。一方、runner は repo-local basetemp を明示するため、git コマンドが親 worktree を発見し、fixture root と worktree top の境界がずれた。
停止が公開停止になった理由
News-Grasp は公開前 gate をすべて通過してから digest/data commit、docs 生成、push に進む設計である。pytest-static の非0終了により、runner は blocked_local_contract_failure として通常公開を止めた。
repair が救えなかった理由
repair matrix は pytest-static を typed_fatal / blocked_local_contract_failure として扱い、LLM repair worker を起動しなかった。これは安全側の停止であり、契約テスト不整合を公開へ進めないための guard が働いた状態である。
2次
二次的に見つかった問題

当初の RecoverOnly でも同じ pytest-static 契約不整合が再現した。日次コンテンツ側の URL liveness、record schema、digest/articles reconcile は修正後の再実行で通過しており、二次的な外部 API block や YouTube quota block は確認されなかった。

04

直近改修・過去障害との関係

直近改修
TTS / BGM / publish hardening により、公開前 gate は以前より強くなっていた。これは壊れた成果物を公開しないためには正しいが、pytest temp 未固定という環境依存が fatal gate へ昇格した。
過去障害との関係
過去にも repo runner と live runner の drift が問題になっていた。今回も最初は repo/live hash が不一致であり、repo 修正だけでは翌朝の Scheduled Task に反映されない危険があった。
過去障害との関係
2026-06-18 の pytest-static 障害は runner の temp 境界だった。今回は runner 側ではなく、audit_runtime_model_dependencies が nested root を扱う境界で失敗した。どちらも 非対話 runner と local test の環境差が gate に出る class である。
今回の位置付け
単独の pytest 事故ではなく、公開前 gate 強化、bounded repair scope、live runner 同期、RecoverOnly 運用の境界で起きた運用系障害である。
05

恒久対応方針の網羅性と完璧性の担保

完璧性の定義

ここでいう完璧性は「未知の全障害が絶対に起きない」ではなく、今回と同じ class の障害が再導入された場合に、公開前または契約テストで検出できること と定義する。今回の class は nested repo-local basetemp、git worktree top と指定 root のズレ、fixture root の候補走査漏れ、typed fatal 後の RecoverOnly 再開である。

Layer 1
失敗を表現しにくくする

git 出力は worktree top から実パスへ戻し、指定 root 配下の候補だけを走査する。

Layer 2
境界で集約する

runner の pytest gate に固定し、個別手順ではなく実行経路で担保する。

Layer 3
契約テストで固定する

runner から basetemp 固定が消えたら契約テストが fail する。

Layer 4
live 同期を完了条件化する

repo runner 修正後は install と SHA256 一致を必ず done criteria に含める。

Layer 5
公開 inventory を列挙する

7カテゴリ digest、Summary、DeepDive、docs、publish-status、URL sentinel を確認。

Layer 6
scope 外修復を止める

bounded repair が範囲外を触った場合は公開しない。今回もこの防御で未検証 push を防いだ。
