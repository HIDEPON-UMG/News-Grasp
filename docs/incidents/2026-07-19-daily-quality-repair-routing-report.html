Fault boundary · 停止した工程

停止境界は daily-quality。この gate は公開前の記事鮮度、card 構造、search audit 整合、thumbnail の欠落を同じ日付で検出する。今回の問題は gate 自体の過検知ではなく、validator → coverage matrix → registry → 同一 gate 再検証の接続が一部の issue code と Markdown 構造に届いていなかった点にある。fallback publish は行われず、壊れた公開面は生成されなかった。

02

問題の詳細と、なぜ起きたか

直接原因
二回目の daily-quality は、FX TOP の鮮度違反、Game の selected_total と digest 件数差分、Game/IT の thumbnail 欠落、FX card #04 の強調不足を検出した。runner は既存の category-card-emphasis-patch を一度実行したが、同じ signature が残り、retry limit に到達して停止した。
なぜ起きたか
top article date ... TOP STORY must be today's or yesterday's article が structured issue code へ落ちず、coverage matrix では stale URL 系へ寄りやすい状態だった。さらに 構造化レーン本文の 【事実・概要】： 形式を emphasis repair がスキップし、separator が崩れた digest では card 境界も維持できなかった。
二つ目の停止理由
公開生成側では tools/generate_pages.py の thumbnail parser が ![thumb](...) に強く寄っていた。実 digest は記事タイトルや日本語 alt を持つ Markdown 画像を含むため、画像自体が存在していても「thumb 欠落」として扱われ、public card と OGP の入力が fallback 側へずれる危険があった。
公開停止になった理由
daily-quality は publish 前の品質 gateである。Article freshness、search audit、thumbnail、card emphasis は public surface に直接出るため、runner は DeepDive 以降へ進まず停止した。これは正しい fail-close で、NoPublish や fallback publish による成功扱いは発生していない。
確認した非原因
OAuth、YouTube quota、GitHub Pages outage、DeepDive renderer、TTS engine、Podcast finalize が直接原因ではない。復旧 run では summary-reflection、daily-quality、generation-quality、URL liveness、record-schema、pytest-static、DeepDive required、public-html、availability、Podcast verification、playlist audit、publish-complete が最終的に通過した。
2次
二次的に見つかった問題

同じ日付の復旧中に generation-quality と record-schema の built-in repair も動いた。これらは最終失敗原因ではないが、runner が複数 gate の修復 ledger を保持しながら publish-complete まで到達できることを同じ run で確認した。

04

直近改修・過去障害との関係

2026-07-06 との関係
selected_total mismatch を structured repair path に上げた過去障害と同じ方向の再発である。ただし今回は stale TOP、structured lane、thumbnail parser が同時に重なったため、search audit metadata patch だけでは不十分だった。
2026-07-11 との関係
Repair Decision Debt Covenant の対象である。validator emits structured issue、coverage matrix owns routing、registry owns handler/scope integrity、runner preserves ledger という分担を今回の stale TOP にも拡張した。
2026-07-18 との違い
前日は pytest-static の UI/policy gate。今回は daily-quality の content/repair routing gate。どちらも fail-close は正しく働いたが、今回の恒久対策は renderer の見出し分割ではなく、daily-quality issue metadata と registry mutation の境界に置いた。
履歴反映
本 incident は tools.historical_failure_scenarios に追加し、tests/test_historical_failure_scenarios.py で登録を固定した。docs/incidents の public report corpus と historical matrix がずれないことも同じ test で確認する。
05

恒久対応方針の網羅性と完璧性の担保

完璧性は「当日だけ手で直す」ことではなく、同じ daily-quality failure class が次回 runner で typed issue と deterministic repair と同一 gate 再検証へ自然に流れることで担保する。今回は validator、coverage matrix、registry、page parser、historical matrix、incident report validator を同じ変更単位で接続した。

LAYER 1
構造

stale TOP を unknown にしない。validator の出力から issue code と artifact metadata を一貫して取れるようにする。

LAYER 2
境界

digest repair は card separator と structured lane label を壊さず、page parser は Markdown alt の文言に依存しない。

LAYER 3
運用

post-daily-quality resume で DeepDive、TTS、docs、Podcast、public verification まで到達し、fallback publish を成功扱いしない。
