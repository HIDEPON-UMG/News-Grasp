02

問題の詳細と、なぜ起きたか

直接原因
過去障害 matrix は全 incident を列挙していたが、詳細監査は 4レーンごとの読み取り証跡 ではなく、scenario field をつなげた summary だった。
なぜ起きたか
corpus coverage と evidence-level audit を同じものとして扱い、全件列挙を詳細再監査と誤認できる構造が残っていた。
停止/品質障害になった理由
この不足が残ると、過去障害の横並び調査をしたつもりで、runner wrapper、repair registry、state manifest、incident report の片側だけを見落とす。
補足
今回の対応は新しい E2E を増やすことではなく、過去障害から導いた最小検出点を fixture / contract / runtime E2E に分け、どのレーンで捕まえるかを固定する。
2次
二次的に見つかった問題

artifact collision と full runner 障害を分離した後も、過去障害全体に同じ4レーンを再適用した証跡が不足していた。これは future incident が report だけ整って runner/repair/state を見落とす再発経路になる。

完璧性の定義

今回の完璧性は、過去障害を「日付と原因の一覧」で終わらせず、同一 incident を4レーンで読んだ証跡 と、再発時にどの fixture / runtime E2E / report validator が捕まえるかを明文化することである。

Layer 1
matrix を正本化

scenario 追加なしに新規 report を通さない既存 contract を維持。

Layer 2
4レーンを型化

runner/repair/state/report の欠落を audits test で fail させる。

Layer 3
followup を分岐

runtime_e2e_required と fixture_required を混ぜない。
