02

問題の詳細と、なぜ起きたか

直接原因
当日 digest のうち Manufacturing と Mobility に空 thumbnail が残り、Economy には日付 window 外の stale URL が残った。さらに resume 後、tests/test_home_variant_b.py が 2026-06-29 の特定記事語句を固定していたため、2026-06-30 の実データで pytest-static が stale assertion として停止した。
なぜ起きたか
thumbnail / freshness / article count は日次データ依存で変動するが、初回自動 repair は summary emphasis までしか解決できず、実データそのものの refill 未解決を残した。また UI テストは TOP STORY の構造契約ではなく 6/29 の京セラ記事に依存しており、翌日データに追従できなかった。
停止/品質障害になった理由
公開前 gate は、空 thumbnail、stale URL、digest/articles 不一致、個別テスト失敗のいずれも公開ブロッカーとして扱う。これは 公開後の破損を防ぐ正しい停止だが、復旧が手動判断に落ちたため運用遅延になった。
確認済み非原因
YouTube OAuth は auth_status=ok、GitHub push は cf0a4ee..0c7f13a main -> main で成功、Pages workflow は conclusion=success。したがって __OAuth 失効、GitHub 認証、Pages deploy 自体は原因ではない__。
二段目停止の補足
pytest-static の失敗は TOP STORY / TOP FEATURE UI の実装そのものではなく、2026-06-29 固定のテスト前提と、2026-06-15 DeepDive の historical source URL 404 が当日公開 gate に混入したことだった。復旧では特定記事固定を構造契約へ戻し、historical URL は同一 ANN 配信の生存 URL へ置換した。
2次
二次的に見つかった問題

URL liveness の --match-session は data/_session_urls.json が不在または空のため session 照合を skip し、従来 gate のみで継続した。今回の完走には影響しなかったが、__PostToolUse hook の session URL 証跡が当日 runner に供給されていない__可能性が残る。加えて、resume 実行時に repo 側 runner と live runner の SHA がズレており、今回は本番停止回避のため repo runner を直接起動した。

04

直近改修・過去障害との関係

TOP STORY 改修との関係
TOP STORY / TOP FEATURE の SCORE NOTE / KEY NUMBERS / SIGNALS 対応は、当日データで key numbers が抽出できない article に当たると表示順契約を満たせない可能性があった。今回 fallback を入れ、構造契約を当日データへ適応させた。
E2E 運用との関係
今回の復旧では、修正後にフル E2E / NoPublish を回していない。これは直近の浪費指摘を受けた運用補正に沿う。実行したのは失敗 gate と同一の pytest-static、および runner の停止点以降 resume だけである。
過去 DeepDive URL 障害
2026-06-15 DeepDive の historical URL 404 は当日成果物ではないが、全静的テストの対象になっているため当日 publish を止めた。過去 source URL の劣化が未来の公開 gate に混入する構造であり、URL validator の役割としては正しいが、修復単位は historical digest の source 置換に閉じる必要がある。
非原因
LLM usage limit、YouTube OAuth、GitHub Pages workflow、GitHub Release audio upload、Web Push worker は最終復旧時点で Green。batch は publish_complete まで到達したため、最終障害として残った外部ブロッカーはない。
05

恒久対応方針の網羅性と完璧性の担保

完璧性の定義は、当日データの変動、historical URL の劣化、表示契約テストの stale 化、resume 誤用の四系統を次回以降の publish blocker として再発させないことである。単に今回の 2026-06-30 を公開できたことだけでは恒久対応完了とは扱わない。

LAYER 1

データ品質 predicate の統一

空 thumbnail、stale URL、digest/articles count、search_audit selected_total を同じ判定述語で評価し、修復後も同一 validator で確認する。

LAYER 2

UI 構造契約の一般化

TOP STORY / TOP FEATURE テストは特定記事語句ではなく、SCORE NOTE、KEY NUMBERS、SIGNALS の存在と順序を検証する。

LAYER 3

resume 境界の明確化

停止点が明確な場合だけ、deepdive または post-deepdive を使う。フル E2E / NoPublish は修正後確認として使わない。

LAYER 4

historical URL 劣化の扱い

過去 DeepDive URL が落ちた場合、当日 publish を止める根拠と、historical source 修復の最小単位を reportable に分ける。

LAYER 5

live runner drift の整理

本番を止めないため repo runner 直接実行で復旧したが、平時に live runner と repo runner の同期状態を戻す必要がある。

LAYER 6

session URL 証跡

data/_session_urls.json が空でも gate は従来方式で継続するが、session 照合欠落は別途復旧対象として扱う。
