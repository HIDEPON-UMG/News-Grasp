Fault boundary · 停止した工程

停止点はコンテンツ生成ではなく、公開前 gate の batch-slo。pytest-static は 07:14 に Green だったが、06:00 起動からの処理時間が window_sec=4294 となり、上限 3600 秒を超えた。runner は SLO 超過を公開前の typed Red として扱い、遅延した通常 run のまま push しない判断をした。日次バッチは起動済みで、digest・Summary・DeepDive・audio-script までは生成済みだったため、generate_pages.py と git push に到達せず、公開面は前日のまま残った。

02

問題の詳細と、なぜ起きたか

直接原因
runner の通常 run が公開前に 3600 秒 SLO を超過し、tools.validate_batch_slo が window_sec=4294 limit=3600 を返した。
なぜ起きたか
06:46 の generation-quality で audio-script 欠落が見つかり、targeted Codex repair が 155,084 tokens を使って 07:03 まで走った。これは既存 repair path の範囲内だったが、通常日次 run としての公開時間予算を使い切った。
停止が公開停止になった理由
News-Grasp は公開前 gate をすべて通過してから digest/data commit、docs 生成、push に進む設計である。SLO 超過により、runner は blocked_slo_violation として公開を止めた。
repair が救えなかった理由
SLO gate は成果物欠落や schema mismatch ではなく run 全体の時間予算を判定する。通常 run の途中では残り工程を短縮して Green に倒せないため、安全側の停止として扱い、別 run の RecoverOnly で同じ gate を最初から再検証した。
2次
二次的に見つかった問題

6:40 監視中には generation-quality の missing_artifact、record-schema の thumb_invalid_or_missing が見つかったが、いずれも coverage matrix と deterministic/targeted repair で収束した。二次問題は最終停止原因ではないが、通常 run の SLO 超過に寄与した。

04

直近改修・過去障害との関係

直近改修
直近の repair hardening により、missing artifact や record schema 欠落は公開前 gate 内で修復されるようになっていた。これは壊れた成果物を公開しないためには正しいが、targeted repair の長時間化によりSLO gate が fatal 化した。
過去障害との関係
2026-07-14 も generation-quality / podcast 周辺の修復で通常 run が長引いた。今回も repair は収束したが通常 run の時間予算を超えた ため、SLO と修復予算の境界を incident として扱う必要がある。
2026-07-13/14 障害との関係
2026-07-13/14 の復旧で、RecoverOnly と public verifier の直列実行が重要になった。今回も生成済み成果物を活かす RecoverOnly 復旧により、頭から再生成する損害を避けた。
今回の位置付け
単独の生成事故ではなく、公開前 gate 強化、targeted repair の実行時間、SLO、RecoverOnly 運用の境界で起きた運用系障害である。
05

恒久対応方針の網羅性と完璧性の担保

完璧性の定義

ここでいう完璧性は「未知の全障害が絶対に起きない」ではなく、今回と同じ class の障害が再導入された場合に、公開前 gate と 6:40 automation が検出し、RecoverOnly で公開 Green へ戻せること と定義する。今回の class は SLO 超過、targeted repair 長時間化、通常 run と復旧 run の境界、通知 skipped_not_normal の扱いである。

Layer 1
SLO を fatal として維持

遅延した通常 run を正常公開扱いにせず、別 run の RecoverOnly で再検証する。

Layer 2
repair 時間を観測する

targeted repair の token・wall-clock を gate attempts と runner log に残す。

Layer 3
6:40 automation で分岐

継続中でも artifact 増分、stage、同一失敗反復を見て異常継続に倒す。

Layer 4
RecoverOnly を正式復旧 path にする

生成済み成果物を再利用し、同じ gates、TTS、Podcast、publish verify を再通過する。

Layer 5
公開 inventory を列挙する

当日必須カテゴリ digest、Summary、DeepDive、docs、publish-status、URL sentinel を確認。

Layer 6
public verifier を直列実行

canary 競合を避け、live readiness、publish-complete、public surface を順番に通す。
