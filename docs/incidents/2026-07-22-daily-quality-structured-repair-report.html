Fault boundary · 停止した工程

停止点は daily-quality の JSON issue 解析境界である。validator は data/search_audit/2026-07-22/ai.json の dropped reason 欠落と、data/articles.jsonl の stale follow-up を検出した。しかし JSON payload の issue_code が unknown のままだったため、既存 matrix row がある障害を未知障害として扱った。その結果、Stage4 DeepDive、TTS、docs 生成、Podcast、push は未到達になった。

02

問題の詳細と、なぜ起きたか

直接原因
structured JSON issue の issue_code が unknown の場合、message から既存 issue code と artifact metadata を復元していなかった。validator は既知の障害を出していたが、orchestrator 側で unknown に固定された。
なぜ起きたか
line regex fallback は ERROR: 行向けに整備されていたが、JSON issue の message を同じ分類境界へ通す契約テストが不足していた。そのため search audit metadata と follow-up review が matrix に届かなかった。
停止/品質障害になった理由
daily-quality は公開前の Definition of Done gate であり、dropped reason 欠落や古い follow-up の未レビュー掲載を許容しない。unknown repair class は spec 上 typed fatal であるため、runner は壊れた公開を押し通さず停止した。
補足 / 非原因
外部 API、YouTube quota、GitHub Pages outage、OAuth 再同意は直接原因ではない。公開復旧後の verify_public_surface は remote HEAD、Deploy Pages、audio、primary Podcast、DeepDive Podcast、distribution manifest を Green とした。つまり 外部境界ではなく repo-local repair routing の defect である。
2次
二次的に見つかった問題

RecoverOnly の選択だけでは DeepDive 欠落を埋められず、generation-quality で止まることを確認した。さらに audio-script は 2309字で背景観点不足だったため、既存 audio-script-length-patch を使い、DeepDive は RecoverOnly ではなく -ResumeFromStage deepdive で生成した。これは復旧判断の誤りではなく、各 resume mode の責務境界を確認した結果である。

04

直近改修・過去障害との関係

2026-07-19 との関係
過去の daily-quality repair routing 障害では、structured metadata の保持が課題だった。今回も同じ系統であり、validator が持つ意味を repair matrix が失うと復旧不能になることを再確認した。
2026-07-21 との関係
digest-record sync の復旧では、daily-quality が record truth と digest のズレを検出した。今回も公開前 gate は正しく止めており、問題は 検出ではなく routing と deterministic handler の受け口にあった。
fallback 禁止との関係
今回の復旧は fallback publish ではない。daily-quality を Green に戻し、DeepDive、TTS、Podcast、distribution manifest、public verifier まで同じ日付で揃えた。News-Grasp の Definition of Done に沿う復旧である。
新規バグ候補
JSON issue の message 再分類契約と、dropped_reason_summary だけを持つ audit の deterministic repair 契約が不足していた。今後は unknown をそのまま fatal 化する前に、message の既知パターンを復元できるかを matrix 側で固定する。
05

恒久対応方針の網羅性と完璧性の担保

Completeness definition

完璧性は、単に今日の artifact を直すことではない。validator → coverage matrix → registry → runner → public verifier の全レーンで同じ issue code、artifact、日付を保持し、同じ failure class が次回は既存 handler へ届くことを指す。

LAYER 1
Validator

JSON issue が unknown でも message には既知の構造が残る。分類境界でそれを捨てない。

LAYER 2
Coverage matrix

search audit metadata と follow-up review を deterministic handler へ routing する。

LAYER 3
Registry

dropped examples だけに依存せず、reason summary を情報落ちなく構造化する。

LAYER 4
Runner

RecoverOnly と stage resume の責務を混ぜず、DeepDive 欠落は生成経路へ戻す。

LAYER 5
Public verifier

URL 200 ではなく publish-complete、public surface、distribution、podcast を同時確認する。

LAYER 6
Report

incident evidence を残し、historical failure scenario と policy で再発時の見落としを減らす。
