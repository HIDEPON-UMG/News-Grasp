02

問題の詳細と、なぜ起きたか

直接原因
goal の完了条件が、復旧済み前提、曜日別必須カテゴリ、Podcast/public URL/SLO の将来 gate を分離できていなかった。Codex はユーザーの最新訂正を受けた後も、復旧作業をやり直すかのような計画を出し、作業統制を破った。
なぜ起きたか
完了条件が「何を作ったか」中心で、現在状態の復旧タスク と 将来の完走判定 gate を分けていなかった。復旧済みの事実を source-of-truth として固定する契約が無かった。
なぜ goal が打ち取れなかったか / 完走扱いになった理由
fallback_ok、局所テスト、ローカル生成、報告書更新が、公開体験全体の complete と混同されうる状態だった。SLO 1時間、370万token級の消費、非対象カテゴリ探索、Podcast/public URL 未検証を complete blocker として固定する gate が足りなかった。
非原因
Game が水曜に必須でないこと、Manufacturing / Economy が土日に必須でないことは仕様として正しい。問題は Game を毎日必須に戻すことではなく、tools.publish_inventory.scheduled_category_ids(issue) から当日必須カテゴリだけを導く実行経路が不足していたことである。
補足
公開済みの非対象カテゴリ artifact が存在しても、それを当日必須カテゴリへ昇格しない。存在してよい過去成果と、今後の runner が生成してはいけない非対象 artifact を分ける必要がある。
2次
二次的に見つかった問題

既存 2026-06-24 レポートは Game を水曜必須と誤読する古い説明を含んでいた。この訂正版では Game は火木土日のみ、Manufacturing / Economy は月火水木金のみを正仕様とし、障害の焦点を goal 完走判定と source-of-truth drift へ戻した。

03

問題の暫定対応内容

検知

ユーザー指摘により、Podcast 復旧済み・日次バッチ復旧済みという前提を Codex が保持できていないことが明らかになった。

Red

Operational Premise Fidelity、publish_inventory --kind categories、runner fan-out、非対象 digest、classify output-file、SLO gate の Red を追加した。

Green

docs/spec.md、tools.publish_inventory、news-grasp-runner.ps1、validate_daily_quality、auto_repair_orchestrator、validate_batch_slo を実装し、関連テストを Green にした。

検証

関連 193 件の pytest が PASS。対象は spec、publish inventory、runner convergence、daily quality、auto repair classify、SLO、newsroom prompt、daily_self_heal、gate_policy、generation quality。

公開

commit / push / live runner sync / public report publish を実行済み。remote HEAD 一致、Pages success、public report 200 + sentinel、SW_VERSION 反映を確認した。

FIX 1
復旧済み前提を spec 化

docs/spec.md に Operational Premise Fidelity を追加し、現在状態と将来 gate の混同を禁止。

FIX 2
曜日カテゴリ正本を CLI 化

tools.publish_inventory --kind categories が当日必須カテゴリだけを返す。

FIX 3
runner fan-out を正本派生へ

7カテゴリ固定配列を消し、Get-PublishInventoryArtifacts -Kind categories から Stage0 / Stage2 を動かす。

FIX 4
SLO / classify を gate 化

失敗 capture を分類器へ渡し、300万token / 3600秒超過を blocked_slo_violation で止める。

04

直近改修・過去障害との関係

source-of-truth drift
過去にも repo 側 runner と live runner、prompt と実行経路、publish inventory と検証対象の drift が障害原因になっている。今回も正本は docs/spec.md ではなく実行 path に反映されて初めて有効である。
fallback_ok
fallback_ok は旧号保護であり通常完走ではない。watcher は既に fallback_ok を terminal success にしない契約を持つが、goal 自走の完了判断も同じ原則に合わせる必要がある。
Podcast
Podcast は復旧済みである。しかし今後の完走判定では、復旧済みだから検証不要ではなく、復旧済み状態を再作業へ戻さず gate として確認する。
SLO
ユーザー期待値は1時間であり、2時間で半分未満や 370万token 級の消費は実用品質を下回る。SLO は感想でなく validator と runner status へ入れる。
05

恒久対応方針の網羅性と完璧性の担保

完璧性は、復旧作業の再実行ではなく、未達完走扱いが再発できないこととして定義する。正本は tools.publish_inventory.scheduled_category_ids(issue)、完走判定は publish_complete / Podcast / public URL / DeepDive / SLO を含む gate、報告は PASS/FAIL 証跡つき Acceptance Matrix で閉じる。

LAYER 1
仕様正本

曜日別カテゴリ、非対象 artifact、復旧済み前提を docs/spec.md と contract test へ固定。

LAYER 2
実行正本

runner は 7カテゴリ固定を持たず、publish_inventory CLI からカテゴリを取得。

LAYER 3
検証正本

validate_daily_quality は非対象 digest を typed error として扱い、missing と混同しない。

LAYER 4
分類正本

auto_repair_orchestrator は空 output でなく失敗 capture file を読む。

LAYER 5
SLO 正本

validate_batch_slo が token と duration を検査し、runner が blocked_slo_violation で止める。

LAYER 6
報告正本

障害レポートは復旧済み状態と将来 gate を分け、誤前提を残さない。

今回の恒久対策は、復旧作業ではなく完走判定の欠陥を直すものである。 公開面と Podcast は既に復旧済みであり、現在状態の復旧タスクとして扱わない。 一方で、今後の runner が complete を名乗る場合は、public URL、Audio、Daily Podcast、DeepDive Podcast、publish_complete、remote HEAD、SLO を検証対象から外してはならない。 Game は火木土日のみ、Manufacturing と Economy は月火水木金のみという仕様を、docs/spec.md、publish_inventory、runner fan-out、repair scope、validate_daily_quality、contract test へ接続した。
