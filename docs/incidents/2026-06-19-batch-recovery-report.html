Fault boundary

停止境界は daily-quality と後続の digest-articles-reconcile / url-liveness であり、壊れた成果物を publish しない設計は機能した。一方で repair worker が artifact scope 外の report や audit JSON へ触り、同じ recovery を複数周させた。

02

問題の詳細と、なぜ起きたか

直接原因
古い記事 URL と articles.jsonl の当日 URL 集合がずれ、公開前 gate が停止した。
二次要因
bounded repair 中に token_revoked / refresh_token_invalidated が発生し、認証復旧まで repair が止まった。
非原因
publish 失敗や GitHub Pages 障害ではない。公開系は gate 通過後に実行し、remote HEAD と public sentinel は一致した。
2次

認証切れは初回停止の原因ではなく、復旧作業を遅らせた二次要因 と整理する。

04

直近改修・過去障害との関係

直近改修
URL liveness、DeepDive 必須化、digest/articles 突合 gate の強化により、過去より厳しく停止した。
過去障害
Summary/カテゴリだけで完了扱いにする事故を防ぐため、DeepDive と公開 sentinel を完了条件へ含めた運用と整合する。
今回の学び
gate の強化自体は正しいが、repair worker の artifact scope が狭すぎると 修復済みでも周回失敗になる。
05

恒久対応方針の網羅性と完璧性の担保

完璧性は「何度も repair を回すこと」ではなく、公開条件と repair 許可範囲を同じ artifact inventory に揃えることで担保する。

LAYER 1
inventory 統一

publish 必須成果物と repair 許可成果物を同じ定義から取る。

LAYER 2
認証事前 gate

LLM repair 前に認証状態を確認し、token revoked を早期に切る。

LAYER 3
手動 publish 手順

同一 gate が通過済みなら runner 周回を止め、publish verify に進める。
