# News-Grasp 障害レポート デザインシステム（BUG_REPORT_DESIGN.md）

> 日次公開障害レポートの統一デザイン仕様。
> 参照実装: `障害レポート.dc.html`（2026-06-18 版）
> トーン: **navy × gold × paper**。本文・ラベルは Sans/Mono、見出しと結論は Serif（明朝）。
> 制約: 単一 HTML で完結。外部 CDN・外部画像に非依存（Web フォントのみ許可）。

---

## 0. 設計原則（毎回これを守る）

1. **結論ファースト** — 冒頭に「どこで・なぜ止まったか」を1文で断定する `結論` ボックスを必ず置く。読み手（運用者本人）が3秒で全体を掴めること。
2. **横スクロールを作らない** — 工程図は固定幅 SVG を使わず、折返す HTML/CSS ノード列で表現する。あらゆる幅で破綻しないこと。
3. **コード/パスは必ず折返す** — Windows パスや長い識別子で行が崩れないよう、`code` は `word-break:break-all; overflow-wrap:anywhere` を徹底する。
4. **余白は密度のために使う** — 余白は「空ける」ためでなく「階層を作る」ために置く。意味のない大余白を作らない。セクション間 `52px`、要素間は 4px グリッド。
5. **色は状態にだけ使う** — 装飾目的の色を足さない。赤=停止 / 緑=完了・復旧 / 琥珀=注意・計画 / navy=構造 / gold=アクセント。
6. **強調は論点を固定するために使う** — §9 の News-Grasp 強調ルールに従う。装飾としての強調は禁止。

## 2. タイポグラフィ

### フォント（3種のみ）
| ロール | フォント | 使いどころ |
|---|---|---|
| Serif（明朝） | **Noto Serif JP** | **h1・各セクション見出し（h2）・結論本文**。読み物としての可読性と品位。ここをゴシックにしない。 |
| Sans（ゴシック） | **Noto Sans JP** | 本文・表・カード・キャプションなど大半のテキスト。 |
| Mono | **JetBrains Mono** | ラベル（英大文字）・セクション番号・時刻・状態タグ・`code`・パス。 |

ロード（`<helmet>` 内、これ以外のフォントを足さない）:
```
https://fonts.googleapis.com/css2?family=Noto+Sans+JP:wght@400;500;700;900&family=Noto+Serif+JP:wght@500;600;700;900&family=JetBrains+Mono:wght@500;700&display=swap
```

### Serif / Sans の使い分け（重要）
- **見出しと結論 = 明朝**。日本語の長い名詞句・タイトルは明朝の方が字面が落ち着き、太ゴシックより読みやすい。
- **本文・UI ラベル = ゴシック / モノ**。情報密度が高い箇所はゴシックで走査性を確保。
- 明朝見出しには **負の字間（letter-spacing マイナス）を付けない**。行間は広め（h1: `1.4`、結論本文: `2.0`）。
- h1 は大きく（screen 基準 `44px`）。小さくして窮屈に見せない。

### 改行ルール（見出し・短い強調句で必須）
**意味の塊を改行で分断しない。** 特に日本語＋ラテンの複合語は1単位として扱う。
- 見出しは `word-break:keep-all`（文節・単語の途中で折り返さない）を基本にする。
- 改行してよいのは**文節の境界だけ**。許可したい位置に `<wbr>` を置き、それ以外では折り返さない。
- **日本語＋ラテンの複合語**（例: `公開前 gate`、`pytest-static gate`、`live runner` など、和語と英字が空白で繋がる用語）は、間の半角スペースで改行されないよう **塊ごと `white-space:nowrap`**（または `&nbsp;` で連結）する。「公開前」だけが行末に残り「gate」が次行頭に落ちる、といった分断を禁止する。
- 鉤括弧（「…」）・括弧の途中、助詞の直前など、読みの塊を割る位置で改行しない。
- 適用対象は h1 / h2 などの見出しと、`**…**` / `__…__` で囲んだ短い強調句。長い本文段落は通常の禁則処理に委ねてよい。

### タイプスケール（screen / 1040px sheet 基準）
| 要素 | font | size / line-height / weight |
|---|---|---|
| h1（レポート表題） | Serif | `34px` / `1.42` / `900` |
| h2（セクション見出し） | Serif | `22px` / `900`（navy 帯に paper 文字） |
| 結論本文 | Serif | `15px` / `2.0` / `400` |
| 本文 | Sans | `14px` / `1.9` / `400` |
| カード本文・表セル | Sans | `12.5–13px` / `1.75` / `400` |
| キャプション | Sans | `11–12px` / `1.5` / `400–500` |
| セクション番号 | Mono | `16px` / `900` / gold |
| ラベル（EN, 大文字） | Mono | `10–11px` / `letter-spacing .12–.18em` / `700` / 大文字 |
| インラインコード | Mono | `0.86em` / 折返し必須 |

## 3. レイアウト

### ページ構造
```
navy topbar（3px gold 下罫）
  └ 左: News-Grasp · Incident Report   右: 日付 / Daily Batch
sheet（白・max-width 1040px・上下 margin 32px・padding 56px）
  ├ header（paper 帯。label → h1 → 結論ボックス）
  ├ KPI ストリップ（4 連）
  ├ 01 … 06 セクション（navy 見出し帯 + 本文）
  └ footer（mono・1行・muted）
```

### 寸法
- 本紙幅: `max-width: 1040px`、内側 `padding: 56px`。
- セクション間: `margin-top: 52px`。
- セクション見出し: navy 帯（`#181C2A`・角丸 `8px`・`padding:15px 22px`）に `番号(gold) + h2(paper)`。
- スペーシング基準: **4px グリッド**（4 / 8 / 12 / 14 / 16 / 18 / 22 / 24 / 32 / 52）。
- 角丸: カード `8px`、囲みモジュール `12px`、ピル/タグ `999px`、コード `3px`。
- 影は本紙のみ（`0 1px 4px rgba(0,0,0,.1)`）。要素には影を多用しない。

## 4. コンポーネント

すべて**インラインスタイル**で実装する（クラス CSS を使わない＝ストリーミング即描画のため）。

### 4.1 結論ボックス（必須・冒頭）
- paper ヘッダー帯の中に置く。白地・`1px #EBD9B6` 枠・左 `3px gold` 罫、右側だけ角丸。
- 左に Mono ラベル `結論`（gold-dark）、右に明朝本文。
- 役割: レポートの1文要約。ここだけ読めば結論が分かる。

### 4.2 KPI ストリップ
- `1px hairline` 枠 + 角丸 `8px`、中は `repeat(4,1fr)` を縦罫で分割。
- 各セル: Mono ラベル（状態色）→ 数値 `24px/900`（状態色）→ muted キャプション。
- 標準4項目: **Started / Stopped / Recovered / Published**。Stopped は error tint、Recovered は success tint。

### 4.3 工程図（Workflow Map）— 本レポートの核
横スクロールを作らず「いかにも工程図」に見せるための規則。
- 囲みモジュール（`module-bg #FBFAF6`、`12px` 角丸、`1px hairline-soft`）に入れ、独立した図として隔離する。
- 右上に**凡例**を必ず置く: `✓ 完了` / `✕ 停止` / `○ 未到達`。
- パイプラインは2本に分ける: `① Daily pipeline`（停止まで）と `② Recovery pipeline`（復旧）。各見出しは Mono・状態色。
- **ノード**: `flex:1 1 116px; min-width` で並べ、間に gold の矢印 `→`。折返し可。
  - 上段に `番号(Mono)` と `状態アイコン`（18px 円）。
  - 中段に Mono サブラベル、太字ノード名、muted 補足。
- **状態表現**:
  - 完了 = 緑 ✓ 円、通常枠。
  - 停止 = 赤2px 枠 + `box-shadow` の赤リング + 上辺に `STOP` ピル + 赤 ✕ 円。最も目立たせる。
  - 未到達 = `opacity .62` + **破線**枠 + 中空 ○ + 文字 dim。「ここまで来なかった」を視覚化。
- 図の下に navy の **Fault boundary** パネルを置き、停止点の説明を1段落で添える。

### 4.4 セクション見出し
navy 帯（角丸）に `gold 番号(Mono 900)` + `明朝 h2(900, paper)`。全セクション共通。

### 4.5 定義リスト（原因・コンテキスト）
- `dl` を `grid-template-columns: 200px 1fr` の行で構成、各行 `1px hairline` 下罫。
- `dt` = Mono 太字（直接原因は error 色、他は ink）、`dd` = Sans 本文 `1.9` 行間。
- 表組みより**定義リスト**を優先（重い表ヘッダーを減らし、読みやすく）。

### 4.6 タイムライン（暫定対応の時系列）
- 左 `2px` 縦線 + 各点に状態色のドット（`box-shadow` で二重リング）。
- 時刻は Mono・状態色、本文は Sans。停止→対応→復旧で色が遷移（赤→琥珀→緑）。

### 4.7 カードグリッド
- 暫定対応 = `2列`、恒久対応レイヤー = `3列`。
- レイヤーカードは上辺 `3px success` アクセント。Mono ラベル `LAYER n` → 太字タイトル → muted 説明。

### 4.8 実行計画テーブル（区分付き表）
- ここだけ navy 塗りヘッダーを使う（`区分 / 対応 / 完了条件`）。
- 区分は**ステータスタグ**: 完了=緑塗り、計画=gold tint 枠。
- セルは Sans `12.5px`、行ごとに `1px hairline`。

### 4.9 コールアウト（callout）
左にステータスタグ（角丸4px・状態色塗り or tint）、右に小見出し+本文。
- `2次`（warning）= 二次的に見つかった問題。
- `OK`（success）= 報告時点の確認。
- 結論・完璧性の定義などは「左罫タイプ」（左 `3px` 状態色罫 + tint 地）を使う。

### 4.10 コード / パス表現（崩さないための規則）
- インライン `code`: 地 `#F1EBDC`、`0.86em`、`word-break:break-all; overflow-wrap:anywhere`。
- navy 地に置く `code`（Fault boundary 等）: 地 `rgba(201,161,85,.18)`、文字 `#EBD9B6`。
- 長い1行のコマンド/パスは navy のコードブロック（`#181C2A` 地、`#D8D2C2` 文字、`11.5px` Mono、折返し）で見せる。

## 5. アイコン / 記号
- 状態は**テキスト記号のみ**で表す: `✓`（完了）`✕`（停止）`○`/中空円（未到達）。絵文字・複雑な SVG は使わない。
- 矢印は `→`（同パイプライン内 gold、未到達区間は dim、復旧は緑）。
- 装飾的なイラスト・アイコンセットは導入しない。

## 6. セクション標準構成（毎回の章立て）
1. **どの工程で問題が起きたか** — 工程図 + Fault boundary パネル
2. **問題の詳細と、なぜ起きたか** — 定義リスト + 二次問題コールアウト
3. **問題の暫定対応内容** — タイムライン + 暫定対応カード
4. **直近改修・過去障害との関係** — 定義リスト
5. **恒久対応方針の網羅性と完璧性の担保** — 完璧性の定義 + レイヤーカード
6. **恒久対応の実行計画** — 区分テーブル + 公開確認コールアウト

## 9. 強調ルール（News-Grasp 共通・必読）

強調は装飾ではなく、**読者がその段落で持ち帰るべき論点を固定する**ために使う。障害レポートでは「その段落の結論」「判断軸・対立軸」「主要な固有名詞・概念」だけを強調する。

### 9.1 3つの記法と表示（記法 → 公開ページ表示）

| 記法（執筆時） | 用途 | 公開ページ表示 | このレポートでの実装 |
|---|---|---|---|
| `[[企業名]]` / `[[人物名]]` / `[[概念]]` | 固有名詞・主要概念を立たせる | **bold + accent 背景** | `<span style="font-weight:700;background:#F6E7C6;border-radius:3px;padding:.04em .3em">…</span>` |
| `[[リンク先\|表示名]]` | 表示名を変えたいときだけ | 同上（表示名を出す） | 同上 |
| `**語句**` | その段落の**結論・最重要メッセージ** | **太字** | `<strong style="font-weight:900;color:#181C2A">…</strong>` |
| `__語句__` | **判断軸・論点・対立軸**（読者が比較すべき観点） | **underline + bold** | `<span style="font-weight:700;text-decoration:underline;text-decoration-color:#C9A155;text-decoration-thickness:2px;text-underline-offset:3px">…</span>` |

> 技術識別子・パス・ファイル名・コマンドは従来どおり `code`（`#F1EBDC` 地）で表す。`[[...]]` の accent 背景は「読者に効く固有名詞・概念」に限り、`code` と二重がけしない。

### 9.2 強調してよい対象
次のいずれかに限る。
- その障害の主因・転換点・争点
- 数字・時刻・gate 判断・確認結果など、読者判断に効く具体情報
- 複数工程を横断する構造変化
- 「なぜ重要か」を一文で表す結論
- 次に見るべき観測点・恒久対応の判断軸

単なる名詞、一般語、雰囲気語、文全体の飾りには使わない。

### 9.3 量の上限
1 段落あたり、強調は**原則 2 箇所まで**。
- 固有名詞の `[[...]]` は必要最小限。既出の同じ固有名詞を毎回 accent にしない。
- `**...**` は **1 段落に 1 回まで**。
- `__...__` は比較軸・観測軸がある場合のみ。
- 太字と下線を同じ短文に乱用しない。

### 9.4 書き方の基準
良い強調は、**強調部分だけを拾っても論旨が追える**。

良い例（このレポートでの運用）:
- `__コンテンツ生成の失敗ではなく__、運用環境依存が **公開前 gate で fatal 化した運用系障害** である`
- `[[News-Grasp]] は公開前 gate を全通過してから push する設計のため、runner は **公開を止めた**`
- `これは __壊れた成果物を公開しないためには正しい__ が、**環境依存が fatal gate へ昇格した**`

悪い例:
- `今日は **重要な** 障害だった`（一般語の強調）
- `[[gate]] が動いた`（雰囲気語）
- `**...** を1文に複数`（結論が割れる）

### 9.5 禁止
- 強調だけで文章を成立させる
- 1 文に `**...**` を複数入れる
- 重要でない一般語を強調する
- 既出の同じ固有名詞を毎回 `[[...]]` にする
- 見た目のために弱い情報を強調する

### 9.6 完了判定
- 強調部分だけ読んでも、その障害の読み筋が分かる
- 強調なしでも本文は自然に読める
- `[[...]]` / `**...**` / `__...__` の役割が混ざっていない
- どのコンポーネント（結論ボックス・定義リスト・タイムライン・コールアウト）に出ても意味が崩れない
